# NAVCORE-SoOP — layout status

Generated by `tools/gen_pcb.py` + `tools/route.py` from `tools/design.py`.
## DO NOT REGENERATE A PLACED AND ROUTED BOARD

**`gen_pcb.py` rebuilds PLACEMENT from scratch, and from-scratch placement is much worse
than the placement this board accumulated by hand.** Measured, when both bucks were
swapped by regenerating rather than editing in place:

| | this board | after `gen_pcb.py` |
|---|---|---|
| crystal to `U1.12` | **4.43 mm** | 15.70 mm |
| `OSC_IN` / `OSC_OUT` | within limit | **27.6 / 25.4 mm, both over** |
| copper under a screw head | clear | C73 at 2.65 mm vs a 2.75 mm cap head |
| CPL rotations | consistent | **FAIL** |
| unconnected | **0 of 472** | **226** |
| `preflight.py` | READY TO ORDER | **NOT READY, 7 blocking** |

None of that damage was to the bucks. It was collateral, and repairing it is the hand
tuning that produced the good board in the first place.

**The same change done in place cost 22 unconnected instead of 226, and left the crystal,
MCU, USB, microSD and both IMUs bit-identical.** Use the in-place tools:

```bash
python3 tools/swap_footprint.py U8 U18   # change a footprint, keep position and rotation
python3 tools/add_part.py                # add a part without regenerating
python3 tools/nudge_part.py              # move one part a fraction of a millimetre
python3 tools/move_net_pin.py            # move a net between MCU pins
python3 tools/route_remaining.py --apply # finish leftovers one DRC item at a time
```

Full regeneration is for a **new revision**, where placement is being designed anyway:

```bash
python3 tools/check_design.py    # validate netlist against the hwdef
python3 tools/gen_sch.py         # schematic
python3 tools/gen_pcb.py         # placement + outline + zones  <-- DESTROYS placement
python3 tools/route.py           # fanout vias, stitching, plane fills
python3 tools/route_stages.py    # staged signal routing, DRC-verified per stage
```

## Routing: freerouting, not my own router

My grid router converged at **64%** and could go no further, because it can only ever
ADD copper — it has no way to move an existing trace aside. Freerouting 2.3.0 has
`ShoveTraceAlgo`, `MazeShoveTraceAlgo` and `PullTightAlgo`, and takes the same board to
**83%** with a fraction of the copper:

| | my router | freerouting |
|---|---|---|
| connections resolved | 64% | **83%** |
| track segments | 13745 | **1932** |
| vias | 462 | **303** |
| DRC errors | 0 | **0** |

Same job, 7× fewer segments — real traces instead of thousands of 0.125 mm grid
fragments.

```bash
tools/route_freerouting.sh          # strip -> keepouts -> DSN -> route -> SES -> apply
```

Requires Java 25 (class file version 69 — Java 21 throws `UnsupportedClassVersionError`)
and `freerouting-2.3.0.jar`. The KiCad side is `pcbnew.ExportSpecctraDSN` /
`ImportSpecctraSES` — **not** `kicad-cli`, which has no Specctra support at all. That is
the detail I missed for several sessions: I checked `kicad-cli`, found nothing, and
wrongly concluded KiCad could not do DSN interchange.

### The last big win was a zone setting, not a router

After freerouting reached 83%, 44 of the 81 remaining items were GND. The cause was mine:
the copper zones were set to **0.25 mm** local clearance while the board's design rule is
**0.15 mm**. That extra 0.1 mm kept the pour out of exactly the tight gaps where the
stranded GND pads sat. Retuning all 14 copper zones to the design rule and refilling took
it from **81 unconnected to 58** in one step, with no new DRC errors.

Worth recording why vias were not the answer there: the stranded pads are U1's VSS pins
and the decoupling packed within 2 mm of every VDD pin. Tested down to a 0.4 mm via,
**zero legal positions** exist beside them - the area is fully occupied. That is a direct
consequence of the Phase B decision to pack decoupling tight; good for the power loops,
hard on the GND escape routes. A real trade, not a bug.

### Two things that were backwards

**Feeding freerouting the existing routing makes it far worse.** With my 13745 segments in
the DSN, fanout escaped 46% of pins, pass 1 took 53 minutes and left 334 violations, and
pass 2 hung for 7 hours. From a **stripped** board: 89% pin escape, passes in 4 seconds,
finished in 17 minutes with **zero** violations. The greedy routing was not a head start,
it was the obstruction — the same fragmentation that stopped my own router.

**Mounting holes are not keepouts.** KiCad writes them as circles on Edge.Cuts, and
freerouting takes only the outermost outline as the board edge, so it routed straight
through them — 7 clearance violations. Explicit rule-area keepouts on all four copper
layers fixed it. Worth noting the rule itself was right: JLCPCB's published 4-layer
copper-to-edge minimum is **0.3 mm**, so the traces were wrong, not the constraint.

More passes keep paying: 8 passes gave 28 unrouted, 24 passes gave 15.

### Phase C — the split L3 power plane

L3 carries `+3V3` as its base pour plus **10 clustered islands** for the secondary rails.
Three things made it work where the first attempt failed:

- **Clusters, not bounding boxes.** A box round `+3V3A`'s pads was an 11 × 36 mm strip
  that bisected L3 and orphaned the `+3V3` base pour on one side — 28 unconnected items
  from one badly shaped zone. Single-linkage clustering plus an aspect-ratio guard
  (reject anything longer than 4:1) keeps islands as compact blobs.
- **Priority ordered by area, smallest first**, so a compact rail always wins where
  regions overlap. Clusters above 260 mm² are skipped and left to the router.
- **Every rail gets fanout vias.** Only `GND` and `+3V3` used to. Since the outer pours
  are GND, **a rail pad with no via has no copper on it at all** — that was the single
  biggest source of unconnected items.

Two clearance figures were doing real damage, both of them mine rather than the fab's:

| | was | now | effect |
|---|---|---|---|
| fanout via clearance | 0.30 mm | **0.20 mm** (rule is 0.15) | fanout 93 → 128 vias; `+3V3` pad coverage 25/48 → 41/48 |
| GND stitching grid | 2.5 mm | **1.8 mm** | stitching 13 → 98 vias |

### The router has converged at 64% — five approaches, measured

| approach | result |
|---|---|
| staged routing, per-stage DRC + rollback | got it to 64% |
| per-net, 5 different via costs, DRC per net | **0 further nets** |
| rip-up-and-retry (`route_ripup.py`) | 2 h 17 min without completing one round |
| multi-target: land on the net's existing copper, not a nominated pad | **+1 net** |
| 5 mil track/clearance instead of 6 mil | **0 further nets** |

The last one is the informative result. If the blockage were *dimensional*, thinner traces
would have opened channels; they opened none. The blockage is **topological** - the copper
already committed has carved the free space into pockets, and a stranded pad's reachable
region does not touch its partner's.

**What a person can do here that this router cannot: push and shove.** KiCad's interactive
router moves existing traces aside to make room. Every algorithm above only ever *adds*
copper to whatever is already there; none can nudge a neighbouring track over by 0.2 mm to
open a channel. That single capability is the difference between 64% and finished, and it
is why the remaining ~80 nets are a GUI session rather than another script.

Rules were reverted to 6 mil afterwards: 5 mil bought nothing, so there is no reason to
give up the manufacturing margin.

### Why a second routing pass used to hang

`route_stages.py` rebuilt connectivity by testing **every pad against every track
endpoint**. With 11k segments on the board after pass 1 that is ~10 million comparisons
per stage, so a pass that took 70 s on an empty board ran for 20 minutes on a routed one.
Spatially bucketing the endpoints fixed it; pass 2 now completes and confirms convergence.

## The RF front end was moved off this board

Measured during layout, not assumed:

| | courtyard area | % of both sides |
|---|---|---|
| flight controller alone | 2213 mm² | **67.5%** |
| flight controller + RF front end | 2516 mm² | **76.8%** |

The routable ceiling for a 4-layer board is roughly 60–65%. **The flight controller alone is already at
the limit**, and the RF section does not fit. The packer could only place it by scattering
U13/U14/U15/U16/FL1/Y2/J9 across the board — which is useless at 1.6 GHz, where the
LNA → SAW → tuner chain has to be contiguous.

This invalidates the plan's "one board carries the RF front end too" premise. It is
also the RF-correct outcome: **an LNA belongs at the antenna**, where it sets the system
noise figure ahead of cable loss. The SoOP front end becomes its own small board.

`SOOP_I_ADC`, `SOOP_Q_ADC` and `SOOP_RSSI` are still broken out to pads, so the H743's
ADCs remain reachable — but note that carrying analogue I/Q over a cable is a compromise.
**This is a decision to make before any respin**, not something to inherit silently.

## Routing is staged, and each stage is verified in isolation

`tools/route_stages.py` routes one functional group at a time, runs real DRC after each,
and **rolls the stage back if it introduced any new error**. Progress is monotonic: the
board is never worse after a stage than before it.

```bash
python3 tools/route_stages.py --list        # show the stages
python3 tools/route_stages.py               # run them all
python3 tools/route_stages.py usb i2c       # run named stages only
```

Order is deliberate — nets where layout affects function go first, while free copper
still exists: crystal → buck switch node → boot straps → IMU SPI1 → IMU SPI4 → SPI3 →
microSD → USB → DShot → I²C → UARTs → CAN → analogue → misc → rails.

Staging is also what made the router debuggable. A 2-net stage producing 19 DRC errors
is obviously a systematic bug; the same defect inside a 197-segment global run just looked
like "dense board, router struggles". Four real bugs were found and fixed this way:

| Bug | Symptom |
|---|---|
| **No-net pads invisible** | pcbnew returns net code **0** for an unconnected pad, not `None`, and 0 was the router's "free cell" marker — so all ~60 NC pins got routed straight over |
| **First-come-wins clearance** | A cell inside *two* nets' keepout halos was claimed by whichever pad stamped first, silently discarding the other's clearance |
| **Via legality ignored tracks** | Via placement checked pads and vias but not tracks, so vias landed 0.14 mm from earlier stages' copper |
| **Circular pad clearance in fanout** | Circumscribed circles meant the other pad of a 0402, 0.96 mm away, blocked every via within 1.02 mm — only 20 of 47 `+3V3` pads could be fanned out, and since the outer pours are GND, a `+3V3` pad without a via has **no copper at all** |

## Known limitations of the generated layout

1. **Placement is functional, not optimised.** Parts are packed into zones by a
   free-rectangle packer. Decoupling caps are in the right zone but not necessarily
   adjacent to the pin they decouple — that wants a manual pass.
2. **The router has converged at 61%, and rip-up-and-retry did not rescue it.**
   A staged pass with a correct already-connected test reports `routed 0` on every
   stage — every remaining pair is either already joined or genuinely boxed in.

   `tools/route_ripup.py` implements the obvious next step: let a blocked net cut
   through existing copper, rip up whoever was in the way, and re-route them next
   round. **It is written and syntactically sound but is NOT viable at this scale** —
   the soft A* can cross other nets, so it explores a vastly larger graph, and a single
   round over ~80 blocked segments ran **2 h 17 min without completing**. It is left in
   the tree, unused, as a documented dead end rather than deleted. It never wrote to
   the board; the committed PCB is byte-identical to the pre-rip-up snapshot.

   `tools/route_nets.py` then tried every remaining net **individually**, five via
   costs each, DRC-verified per net: **kept 0, failed 55.** Not one more net is
   routable, and the board came back byte-identical.

   A flood-fill says why. Free space is not scarce — it is **fragmented**. Starting
   from a stranded pad, the reachable free region is tiny:

   | net | pad | cells reachable (of ~200k) |
   |---|---|---|
   | `USB_DP` | U12.6 | **173** |
   | `M1` | J2.3 | **597** |
   | `I2C2_SCL` | R11.2 | 12874 |

   None reaches its partner. The 24k segments already committed have carved the board
   into islands, and each stranded pad sits in one. This is precisely the condition
   rip-up-and-retry exists to break, and precisely why a greedy router cannot: the
   copper blocking these nets belongs to nets that are already routed and will not
   move. 61% is this router's ceiling on this board, and it is now proven rather
   than assumed.
3. **79 of 124 parts are on the bottom.** The cross-side fallback pushed a lot of
   passives down. Workable, but a manual rebalance would ease routing.
4. **Silkscreen**: passive designators and outlines are on the fab layer, not silk —
   at this density they overlapped everything. ICs, connectors, crystals and buttons
   keep silk designators.

## The IMUs ended up on the bottom, and that changes the firmware

The packer put 81 of 115 placements on the bottom side to make the density work.
Mostly that is harmless - 0402 decoupling does not care which side it is on, and it
is what lets a 45 x 46 mm board carry this much. Two consequences are not harmless.

**The IMU rotations in the hwdef were wrong.** The plan called for orienting the IMUs
to match the rotations MatekH743 declares, so stock binaries are correct out of the
box. Bottom-side mounting breaks that: a part on the far side of the board is its
top-side placement composed with a 180 deg rotation about the board Y axis, so both
IMUs sat 180 deg from what the hwdef claimed. Uncorrected, the vehicle believes it is
inverted - it would not have survived arming.

| | MatekH743 declares | this board is actually |
|---|---|---|
| U2 ICM-42688-P | `ROTATION_YAW_180` | **`ROTATION_ROLL_180`** |
| U3 ICM-42605 | `ROTATION_YAW_270` | **`ROTATION_ROLL_180_YAW_270`** |

`tools/gen_hwdef.py` now reads each IMU's side straight out of the PCB and composes
the correction itself, so the hwdef cannot drift from the layout again. A useful
corroboration that the maths is right: `ROTATION_ROLL_180_YAW_270` is exactly what
MatekH743's own hwdef declares for the far-side ICM-20602 and MPU6000 it carries.

**Bring-up step 4 needs a caveat.** Stock MatekH743 firmware will read both IMUs
inverted. The offset is identical on both, so it is one board-level parameter, not a
per-sensor fix: set **`AHRS_ORIENTATION` to `Pitch180`** when running stock firmware.
The generated `NAVCORE_SoOP` hwdef needs no such parameter - it is already correct.
Pin identity with MatekH743 is unaffected; this is orientation only, not pinout.

## Mounting hardware clearance

The stack screws bear on the board, so this is worth measuring rather than eyeballing.
`tools/check_placement.py` now checks it, against **pad copper** - measuring the
footprint bounding box instead gives a false alarm of roughly half a millimetre,
because that box includes silkscreen and courtyard graphics which are not physical.

| hardware | radius | parts underneath |
|---|---|---|
| M3 cap head, 5.5 mm OD | 2.75 mm | **none** |
| silicone grommet flange, 6 mm OD | 3.00 mm | C25 (2.85), R21 (2.98) |
| M3 washer, 7 mm OD | 3.50 mm | 9 |

**Assemble with the grommets and no washers.** Nothing sits under a bare screw head,
which is the only case where metal would bear on copper. The two parts that clip a
grommet flange do so by 0.15 mm and 0.02 mm, against soft silicone landing on solder
mask over mask-covered pads - an assembly note, not a defect. Only the washer case is
worth avoiding outright.

**U7, the ToF sensor, is clear.** Its optical window sits 4.69 mm from the nearest hole
centre and its closest pad 3.20 mm, so no mounting hardware obstructs its view. Worth
stating explicitly because the packer boxed U7 in tightly - it is surrounded by U6,
R7, C36 and C39, and a directional search found **no** free direction to move it within
2 mm. If that corner is ever re-placed, give U7 room first; it cannot be nudged later.

## The 88% figure was bought by shredding the ground plane

Worth stating plainly because it inverts how the routing progress should be read.
Freerouting was handed all four copper layers as ordinary signal layers, and it used
them:

| layer | segments | routed length | intended role |
|---|---|---|---|
| F.Cu | 764 | 842 mm | signal |
| **In1.Cu** | **325** | **995 mm** | **solid GND plane** |
| **In2.Cu** | **303** | **823 mm** | split power planes |
| B.Cu | 540 | 565 mm | signal |

In1.Cu carries **more routed copper than any other layer on the board** - 995 mm
through the layer the plan specifies as an unbroken GND reference. Two consequences:

**It caused most of the remaining unconnected items.** The GND pour on In1.Cu is
split into 5 islands, and In2.Cu's rails likewise. Every stranded power pad is
downstream of that: of the 56 items left, *all* are power nets. They are a symptom of
the fragmentation, not an independent problem - which is why via-stitching them one
at a time kept failing to fit. The copper is congested precisely because signals are
occupying the plane layers.

**It removes the return path where it matters most.** Routed across In1.Cu are
`OSC_OUT` (17 segments - the crystal), `SOOP_I_ADC` (11 - the analogue I channel),
`SD_CK`, `SD_D0..D3`, `USB_DM_CON`/`USB_DP_CON`, `SPI3_SCK`, and all four DShot
outputs. Those are the exact nets that need a continuous reference plane. A gap under
a 480 Mbps USB pair or a 25-50 MHz SDMMC clock is a real emissions and integrity
problem, and unlike unrouted connections it is invisible in a DRC report.

**The fix** is in `tools/fr_prepare.py`: a board-wide rule area on In1.Cu and In2.Cu
that forbids tracks while still allowing vias and zone fills, so nets reach the planes
but nothing routes through them. `FR_ALLOW_PLANE_ROUTING=1` restores the old
behaviour for comparison.

Expect the headline routed percentage to **fall** - freerouting loses two of its four
layers. That trade is worth taking. Unrouted connections are visible, enumerable, and
finishable by hand; a shredded reference plane is none of those things, and cannot be
repaired after fabrication.

## Three attempts at stitching, and what they were actually chasing

Worth recording because two of the three were solving the wrong problem, and the way
they failed is what pointed at the plane finding above.

`tools/stitch_islands.py` **works and is kept.** It finds pour islands that no via
ties to their plane - the DRC report cannot help here, because every zone reports its
outline origin (100.3, 100.3) rather than the island's position, so they have to be
found geometrically. It placed 3 vias, DRC-clean, 58 -> 56 unconnected.

It also measured why the rest are stuck. The stranded pours are thin snakes weaving
between fine-pitch parts, not blobs: an 18.8 mm2 island had a widest gap to foreign
copper of **0.20 mm**, where a 0.60 mm via needs 0.50 mm. Area is no guide to whether
a via fits. A 0.45 mm via would need 0.375 mm and rescue three more, but the board's
own netclass sets a 0.60 mm minimum, and emitting smaller vias just trades one
unconnected item for two rule violations - so the script reads the constraint from
board setup instead of assuming it.

`stitch_stubs.py` and `stitch_groups.py` were **deleted, premise disproved.** The
first looked for dangling track ends and found six, none viable. The second looked for
connected groups that never reach the plane and found one. Both kept coming up empty
against 56 unconnected items, which was the clue: the fault was not loose ends or
stray groups but the plane layers themselves being full of signal routing. Fixing that
is upstream of all of it. If group-level stitching is wanted again later, note the
trap that made the second script useless - a through via reports `IsOnLayer()` true
for an inner layer whether or not the pour there actually reaches it, so it is not a
usable test for "is this group tied to the plane".

## Measuring the plane trade instead of guessing at it

Three configurations were routed from the same stripped board, 24 passes each, and
compared with `tools/board_report.py`:

| protected | routed | copper on plane layers | GND on In1.Cu | critical nets crossing |
|---|---|---|---|---|
| nothing | **88%** (56 left) | 1818 mm | 5 islands, fragmented | 17 |
| In1.Cu only | 83% (81 left) | 918 mm on In2.Cu | 1 island, solid | 11 |
| **In1.Cu + In2.Cu** | **81%** (90 left) | **0 mm** | **1 island, solid** | **none** |

The middle row is the interesting one, because it is the option that *sounds* best
and is not. Freerouting's own score strongly favoured it - 37 unrouted against 82 for
the fully protected run, better than 2:1. After importing and re-doing fanout that
gap collapsed to 11 connections, because the two-layer board simply needs more fanout
vias and freerouting's "unrouted" counter is not the same measure as KiCad's. Eleven
hand-routed connections is a small price for taking 918 mm of signal off In2.Cu and
the last 11 critical nets off a plane entirely.

**The board now uses the fully protected configuration.** Judge it by the bottom four
rows, not the percentage: 81% with both planes intact is a better board than 88% with
a shredded reference, and the 90 remaining connections are ordinary hand-routing work
with a correct ratsnest.

## Two bugs in fanout that this uncovered

Re-running fanout on the freshly imported board produced 4 DRC errors, and both
causes were long-standing:

**Obstacles were cached per net.** A via placed during the GND pass was appended only
to GND's obstacle list, so the +3V3 pass could not see it. The two passes duly placed
a GND via and a +3V3 via **0.42 mm apart**, where two 0.60 mm vias need 0.75 mm.
Placements now go into one shared list tagged by net - same-net copper still is not
an obstacle, which is what the tag is for.

**The "skip the pad we came from" test was too loose.** It skipped any obstacle whose
rectangle contained the pad origin. `obstacles()` works in bounding boxes, and the
bbox of a long diagonal track can contain that origin too - so `CANL` was skipped
wholesale and a GND stub ran straight across it. It now skips only the source pad's
own rectangle.

Together: 4 errors to 0.

**Also worth knowing:** `tools/route_gnd.py` reports "kept 15" but the board's segment
count does not change, so it is not actually persisting anything. It contributes
nothing on this board and should be treated as suspect until that is chased down.

## Placement defects the adjacency gate found

Adding a missing rule turned up more than the rule was for. `tools/check_placement.py`
went from 23 violations to 26, and several were functional rather than cosmetic.

**The crystal was 24.5 mm from the pins it drives.** C15/C16 were correctly pinned to
Y1 by an adjacency rule, but **Y1 itself was pinned to nothing**, so the packer parked
the whole cluster in a corner. At 8 MHz that is several pF of stray on a
high-impedance node - it pulls the frequency, can stop the oscillator starting, and
runs a sensitive node past the bucks and the DShot outputs. Same class of defect as
VCAP2 being 30 mm from its pin, and the plan is explicit that this class justifies a
respin.

There is no top-side fix: every position within 7 mm of the OSC pins overlaps U1
itself, because those pins are on the package perimeter and the body fills the inside.
The cluster therefore moved to the **bottom side directly beneath them** - the textbook
arrangement, two short vias instead of a long surface trace. **Y1 is now 4.43 mm from
U1.12.**

**The TVS was protecting the wrong thing.** The rule read `D1 -> U8.2, 4.0 mm`,
described as "TVS at the buck's VBAT input". But U8.2 *is* VBAT - the buck's input pin,
not its switch node - and a TVS clamps a surge where it **enters the board**, not at a
downstream regulator. By the time a transient reaches U8 it has already crossed
everything else on VBAT. The rule now targets `J2.2`, the ESC connector's VBAT pin,
and D1 sits **0.00 mm** from it instead of 33 mm away.

Worth being precise about what was *not* wrong: the 5 V buck's switch node (U8.8,
BUCK_PH) was always tight - L2 at 2.78 mm, C22/C23 close behind. The switching loop
was fine; it was the input protection that was misplaced.

**Net effect: 26 violations to 13, DRC still 0**, and nothing left under a screw head.

### Why it does not reach zero

`tools/fix_adjacency.py` converges and then thrashes: R4 shoves C20, R5 shoves R4,
R43 shoves R5, R8 shoves R7, R6 shoves R8, C25 shoves R6. Each fix breaks the previous
one. That is not a bug in the search - it is the honest answer that **the U8/U18 buck
areas are over-subscribed**: more decoupling is required within 3 mm of those pins than
there is room for at this board size. Closing the remaining 13 needs either a larger
board or fewer parts in that corner, not a cleverer placer.

### Three bugs in the fixer, all worth remembering

- **Blockers were parked before the part moved.** Shoving a passive aside while the
  incoming part still sat at its old position let the blocker be parked in the very
  spot the part was about to occupy. 10 courtyard overlaps and 39 clearance errors
  traced back to that ordering. The part is now placed first.
- **Zones were not refilled.** 38 clearance and 34 solder-mask-bridge errors were
  every one of them a pad against a *stale pour*, not a real placement problem.
- **Mounting holes were not keepouts.** The first run pushed C39 to 2.09 mm from a
  hole centre, inside an M3 cap head. The search now excludes a 2.9 mm radius.

## The routing rules were never the ones the design specifies

The single most expensive mistake in this project, and it hid for the whole routing
effort. `fr_prepare.py` copies the board to a temp path to strip it, but **design
rules live in the `.kicad_pro`, which was not copied alongside**. So every DSN
exported `(width 200) (clearance 200)` - KiCad's *default* 0.2 mm - and freerouting
spent hours solving a problem a third coarser than the board actually specifies.

Every conclusion drawn from those runs was therefore measured against the wrong
board, including "76 connections cannot be routed on 4 layers". Correcting it:

| rules actually applied | passes | unrouted |
|---|---|---|
| 0.2 mm (KiCad defaults, by accident) | 24 | 83 |
| 0.10 mm | 24 | 45 |
| **0.1016 mm (4 mil)** | **48** | **38** |

`route.set_rules()` is the only way rules reach the board - editing the project JSON
directly is silently undone, because `board.Save()` rewrites `.kicad_pro` from the
netclass. It now drives off the `TRACK_W` / `CLEAR` constants instead of hardcoding,
and `fr_prepare.py` calls it before both the strip and the export.

### Why 4 mil exactly, and why that is safe here

JLCPCB's 4-layer process: **4 mil (0.1016 mm) trace/space is the free tier**, and
3.0-3.5 mil costs **+20%** on 4-8 layers. Min via pad 0.45 mm, min drill 0.2 mm, with
0.6/0.3 their recommended pairing - which this board already used. 0.10 mm is
3.94 mil, *just* under the threshold, so it would have paid the upcharge for a
0.0016 mm difference that buys no routing density. 0.1016 mm exactly is the right
number.

Thin traces are more prone to micro-fracture, and that concern is legitimate - but it
applies to conductors under mechanical or thermal stress. Here **every power rail runs
on a plane**, so 4 mil carries logic-level current only: about 0.35 A capacity at 1 oz
for a 10 degree rise, against DShot, SPI and I2C loads in the milliamps. Fanout stubs
stay at 0.25 mm and the board is rigid FR4 clamped in a stack, not flexed. If power
were routed as traces, 4 mil would be the wrong call.

`preflight.py` previously encoded 0.127 mm as the JLCPCB limit. That is the **2-layer**
standard - it would have failed a perfectly orderable board.

## Hole clearance is a separate rule, and both routers ignored it

Copper clearance is not sufficient. A via can sit a legal 0.48 mm from an NPTH pad's
**annulus** and still be only 0.18 mm from its **drill**, because the hole is wider
than the copper ring around it. Fabricators check drill-to-drill separately; so does
KiCad, at 0.2 mm. Neither router did.

It appeared twice, from two different sources, which is why it took two fixes:

- **My via placers** checked copper only. `route.hole_shapes()` / `route.hole_ok()`
  now gate `fanout()`, `stitch()`, `fanout_hard.py` and `stitch_islands.py`, and newly
  placed vias are added to the hole list as they go.
- **freerouting's own vias** hit J1's USB-C mounting holes regardless, because
  freerouting has no concept of a drill-to-drill rule. `fr_prepare.py` now emits a
  via-keepout around every NPTH pad (J1 x2 at 0.7 mm, J8 x2 at 1.0 mm), sized as
  drill radius + via drill radius + 0.2 mm + margin.

`tools/fix_drc.py` handles the residue: freerouting reports zero violations against
its own model while KiCad finds clearances of 0.0827 mm against a 0.1016 mm rule -
rounding through the DSN/SES round trip. Those tracks are ripped rather than nudged,
and `route_remaining.py` re-routes them under KiCad's rules, which is the only model
that matters. It never rips a via: a via is usually the only thing tying a net to its
plane.

## What the 25 adjacency "violations" actually mean

Two tools count them differently and it is worth stating which is which, because the
numbers look like a regression and are not. `check_placement.py` measures **pad centre
to pad centre**; `fix_adjacency.py` measures **pad edge to the target pin**. Edge-to-pin
is always the smaller figure, so the same board reads 25 by one metric and 13 by the
other. Nothing got worse between them.

More usefully, the count hides the distinction that matters. Measured against the 5 V
buck (U8), edge-to-pin:

| part | pin | distance | why it matters |
|---|---|---|---|
| C23 | PH switch node | **0.12 mm** | the fast loop - tight |
| C18 | VIN | **0.78 mm** | input ceramic - tight |
| C21 | BOOT | 1.17 mm | fine |
| L2 | PH | 1.45 mm | fine |
| C22 | PH | 2.17 mm | fine |
| C24 | COMP | 2.61 mm | acceptable |
| C17, C19 | VIN | 3.95, 5.71 mm | **bulk** caps - C18 already closes the fast loop |
| R6 | FB | 4.90 mm | **watch this** |
| R8, C25 | COMP | 4.93, 4.95 mm | **watch these** |
| C20 | SS | 8.72 mm | soft-start, a DC ramp - tolerant |
| R4, R5 | EN | 9.52, 8.91 mm | static enable divider - tolerant |

**The high-frequency switching loop is correct.** That is the part that determines
whether a buck is stable and how much it radiates, and C18/C23/L2/C21 are all where
they should be. The far parts are on nodes that do not care: EN is a static input, SS
is a slow ramp, and C17/C19 are bulk behind a tight ceramic.

**The real item is FB and COMP at about 5 mm.** Those are high-impedance,
noise-sensitive nodes next to a switching converter. It is not a blocker -
TPS54331 is a forgiving part and the feedback path is short in trace terms - but if
the 5 V rail shows instability or audible noise on the bench, R6, R8 and C25 are the
parts to move first, not the ones the raw violation count puts at the top.

## Tidying the routing: 6040 segments to 2244

`tools/route.py` routes on a 0.0625 mm grid and emitted **one track segment per grid
cell**. That left 4463 of 6040 segments exactly 0.0625 mm long - 74% of the routing -
almost all axis aligned (1644 at 90 deg, 1092 at -90, 878 at 0, 813 at 180, only 36
diagonals). Every trace the local router laid was a Manhattan staircase of hundreds of
stubs: unreadable in KiCad, bloated in the gerbers, and slow for every geometry pass
since `route.Router` builds its obstacle set from each one.

`tools/tidy_tracks.py` fixes it in three steps, each verified with DRC and rollback:

| | segments | tiny (<=0.07 mm) | 45 deg diagonals |
|---|---|---|---|
| before | 6040 | 4463 (74%) | 36 |
| after | **2244** | 497 (22%) | **955** |

Total copper went 3192 mm -> 3134 mm, and DRC stayed at 0 with the unconnected count
unchanged.

**Deduplicate before merging.** The first attempt only reached 44%, because running
`route_remaining.py` repeatedly had committed overlapping paths - **960 segments with
identical endpoints**. Each duplicate adds two to the degree of both its endpoints, so
the chain walker saw junctions where there were plain joints: 285 points looked
degree-4 and 198 degree-6. Dropping duplicates first is what let the merge reach along
a trace.

**Mitre with a geometry check, not a DRC run.** Chamfering corners blindly at 0.4 of
the shorter leg moved copper into tight clearances and cost **16 DRC errors**. A
whole-board DRC per corner across 606 chains would take hours, so each chamfer is now
tested against the obstacle set in-process and a corner that cannot be cut is left
square. 955 proper diagonals at zero DRC cost.

## Freerouting is deterministic - more passes buy nothing

Worth recording to stop anyone repeating it. On the 6-layer board a 48-pass run reached
13 unrouted. A 150-pass run stopped itself at pass 21 and produced a **byte-identical**
SES - same MD5, same 13. Several hours went into long runs on the assumption that more
passes meant more routing. They do not: freerouting converges and then repeats itself.

Check `md5sum` against a previous SES before committing to a longer run.

## The obstacle model blocked layers that copper cannot reach

Two defects in how obstacles were modelled made the board look far more crowded than it
is, and between them they account for most of the "nothing fits here" results from the
closing tools.

**Pads had no layer.** `route.obstacle_shapes()` returns a pad as a bare rectangle:

```python
for pad in fp.Pads():
    bb = pad.GetBoundingBox()
    out.append(("rect", TOMM(bb.GetLeft()), ...))     # no layer anywhere
```

Every consumer therefore treated a surface-mount pad on F.Cu as blocking copper on
In2.Cu and In3.Cu, which it cannot physically touch. Under a part like U7 (VL53L1X)
that is the difference between "no via position exists" and eight of them: with layers
respected, the `+5V` search went from **0 usable positions to 8** with nothing else
changed. Only through-hole pads and vias genuinely occupy every layer.

**Same-net copper counted as an obstacle.** There is no clearance rule between two
pieces of the same net - they are allowed to touch, and DRC never objects. Checking a
ground trace against the ground pour walls an island in behind its own net, and when a
trace was shoved aside it was reported as "held by" the very via it terminates on. That
single line stopped every cascade dead at the second trace.

`tools/shove.py` carries the corrected model: a `Shape` records `lset`, the set of
copper layers it actually occupies, a via is checked against all six because it is
drilled through the stack, and a trace is checked only against copper sharing its layer
and belonging to another net. `tools/island_route.py` uses the same model.

This is worth being blunt about: several earlier "no path exists" conclusions in this
document were measured against the wrong board. They were honest readings of a model
that was too pessimistic, and anything resting on them deserves re-testing rather than
belief.

## Shoving: moving copper that is already there

Every other closing tool only ever adds copper. It searches for a spot where a via or a
trace fits and gives up when there isn't one. That is not what finishing a layout looks
like - a person grabs whatever is in the way and drags it over.

The remaining connections are exactly that kind. `+5V`'s F.Cu trace has `TOF_XSHUT`
running **0.053 mm beneath it on In2.Cu for the whole 14.75 mm**, so every via position
along that trace is shadowed by the same one trace and is short by the same 0.32 mm. No
search finds a gap, because there is no gap to find.

`tools/shove.py` replaces a victim's middle with a local detour - ramp out, flat run
past the obstruction, ramp back - while leaving **both endpoints exactly where they
were**, so the victim's own connectivity cannot change. Three things it had to get
right:

- **Shove chains, not segments.** `tools/route.py` emits one track per 0.0625 mm grid
  cell, so most "traces" here are hundreds of one-cell stubs. A detour needs room to
  ramp; a 0.0625 mm segment has none, and segment-level shoving failed on *every*
  candidate for that reason alone. Segments are walked into polylines first, exactly as
  `tools/tidy_tracks.py` does, and the detour is cut in by arc length.
- **Cascade the push.** A trace pushed aside lands on its neighbour. `TOF_INT` and
  `TOF_XSHUT` run 0.256 mm apart on In2.Cu with 0.05 mm of slack, so they have to move
  as a bundle. Each round adds whoever the last round ran into and starts again.
- **Refuse to move pads and vias.** Moving a pad moves a part; moving a via breaks the
  layer change it exists to make. If either is in the way the position is rejected
  rather than worked around.

Every shove is verified by whole-board DRC and rolled back individually.

## How the last five connections were actually closed

They were closed one at a time, and each needed a different move. Worth recording,
because four of the five were blocked by the *model* rather than by the board.

**Two ground islands (F.Cu 0.87 mm2, B.Cu 1.22 mm2) — a via fitted all along.**
Both carried a ground pad whose only path to ground they were: a union-find over the
ground net put `U1.49` in a four-item component and `C19.2` in a component of one, and
neither reached a single via. Every previous search had reported "no via fits". With
pads given their real layers and same-net copper stopped from blocking itself, a
0.45 mm via fits in each with **0.33 mm of copper clearance** - not marginal, not a
squeeze, simply invisible to the old model. `tools/island_via.py`.

**+3V3 and +5V — the via did not have to sit on the trace.**
Both were a track on one layer stacked over a one-cell stub on another, and both were
shadowed by the same bundle of five traces on In2.Cu, boxed in by an I2C1_SCL via.
Insisting the via land on the existing trace made them unsolvable. Freed to sit
anywhere and reach back with a routed connector (`--free-via`), +3V3 closed with nothing
moved and +5V closed by shoving `TOF_XSHUT` 0.70 mm aside.

The connector has to be **routed, not drawn straight**. The first fifteen +5V candidates
each closed the connection and each cost the same `tracks_crossing` error: a straight
connector cut across a GND trace, and shoving that trace 0.1 mm only moves where it
crosses. One flood per layer outward from the chain answers every candidate at once.

**The last ground island (B.Cu 1.52 mm2) — the part had to move.**
This one was genuinely sealed. A flood from inside it reached exactly its own 3001 cells
and nothing else. The nearest via position was 0.085 mm short; the traces holding it
could not be shoved because C71's and C72's pads box them in; and `BUCK_EN` could not be
rerouted because **the one via position that would free the island is precisely the
corridor BUCK_EN needs to reach R5.1** - the two are mutually exclusive, so no amount of
routing settles it.

What settled it was moving `C71` **0.20 mm**, which puts its ground pad on the main pour
(`tools/nudge_part.py`). Three things had to be right for that to work:

- **Stitches must be routed.** Of ~1000 positions where C71's pads fit, every one failed
  a straight line back to its old trace end. Routed, 95 survived.
- **The part's own pads are obstacles to each other.** Leaving them out of the flood sent
  C71's ground link straight through its own BUCK9_COMP2 pad - a real short, caught as
  `shorting_items`, not a clearance nit.
- **Copper clearance is not the only rule.** Courtyard overlap and the solder mask web
  both bit, and both are cheap to screen for instead of discovering one slow DRC run at
  a time.

The move slightly **improved** C71's placement (4.36 mm to 4.22 mm from U18.6). Both
figures are still over the 3.0 mm guideline for a compensation capacitor - that is a
pre-existing condition of this cluster, listed as respin items, and the nudge did not
cause it.

## Tools, and which question each one answers

| tool | question |
|---|---|
| `shove.py` | can the copper in the way be pushed aside? |
| `island_route.py` | can a ground island reach the pour on its own layer? |
| `island_via.py` | can a via go inside the island? |
| `rip_route.py` | can the trace in the way be thrown away and re-found? |
| `open_pocket.py` | which trace seals the island, and can it live elsewhere? |
| `nudge_part.py` | can the part itself move? |

They share one obstacle model and one spatial index. That index matters more than it
sounds: without it a point test walks every piece of copper on the board, and the island
escape search - 200k cells against ~6800 shapes - simply never finishes. The first
attempt was killed at 25 minutes having printed nothing.
